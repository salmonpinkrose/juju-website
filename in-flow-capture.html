Case Study

In-Flow Capture

An AI workflow that turns ephemeral team chat — decisions, action items, ideas — into a typed, queryable knowledge base, without a context switch. The AI Companion pattern: capture conversation value before it evaporates.

01 — Demo

What it looks like in practice.

One Slack command (/capture) on a thread → an LLM classifies the salient units, extracts per-type fields, and writes typed rows into a shared Notion database, with an in-thread reply linking the new records. No copy-paste, no context switch.

02 — Problem

Conversation is where work happens. Scrollback is where knowledge dies.

The most valuable organizational knowledge — what we decided, why we rejected the alternative, who owns the follow-up, the spark of an idea — is created as a byproduct of conversation. Capturing it today demands a context switch nobody reliably does. The result is repeated debate, lost commitments, and an organization that has to keep relearning itself.

This is the AI Companion thesis, narrowed to one concrete loop: the message is the input adapter, the structured record is the output adapter — and the model in the middle decides what was worth keeping.

03 — Thinking

The questions that had to be locked first.

Before any code, five questions had to be answered: what to capture, when, who decides visibility, what shape the data takes on the way to retrieval, and how to know any of it works. Products like this fail when those questions are punted to the model — the resulting database becomes unusable within a week, and there is no honest way to tell.

04 — PRD

Four decisions that shaped the product.

The PRD locks scope so the build is measurable. The four decisions below were the highest-leverage — every later judgment call falls out of these.

  • 01 Manual, human-in-loop trigger. The capturer explicitly invokes /capture on a chosen thread. Capture intent is the highest-precision signal available; ambient/auto-capture is much harder to make trustworthy and is deferred to Future Work.
  • 02 Hybrid visibility — shared by default, private by explicit flag. /capture → team KB; /capture private → private. The same human best placed to decide whether to capture is the one best placed to decide who sees it — solving the 1-1 vs. team-KB tension without building a permissions system.
  • 03 Faithful distillation, not curated narrative. No pre-write edit step. "Delete" is the undo, not "edit." Letting users rewrite the AI's distillation reintroduces the manual-summary burden the product exists to remove — and invites revisionism. Quality is a model problem to measure and fix, not a UX gate.
  • 04 A small, atomic taxonomy. Each captured unit is a Decision, an Action, or an Idea. A thread can produce many records, or zero. The Notion page-body template per type is the extraction contract: properties drive filterable views, body holds the rich content cells can't.

05 — How it works

Thin slice, on purpose.

The pipeline is deliberately small: Slack /capture → one LLM call (classify + extract, structured JSON output) → Notion API write. One human action, one model decision, one structured artifact. Inside-out / egress-first build order — Notion was proven first, the Gemini call second, Slack last — so each layer was demoable before the next one existed.

Honest scope

Phase 2 — multi-agent extraction (CrewAI: classifier → extractor) and an MCP server wrapper exposing the capability to any MCP client — is deferred Future Work, not built. The single-call pipeline was chosen specifically so the core could be evaluated before the architecture got more interesting.

06 — Evaluation

What "good" means — and how I measured it.

For a feature whose entire value proposition is trust, accuracy is the product. Evaluation came before iteration — a way to measure capture quality that would not shift after seeing the output.

The harness

Fifteen hand-authored realistic threads, including private 1-1s, an urgent customer escalation, a long messy thread with a launch date that moves four times, and three deliberate noise traps where the correct answer is to capture nothing. For each thread, a written gold standard set before any model output, and a locked precision rubric of seven judgment calls (A–G) defining the boundary between capture and silence: vague reversible promises don't get captured, concrete owned directives do; the same 1-1 setting can produce both rulings.

Baseline

The dominant pattern was immediate: the model was over-eager — capturing polite acknowledgments, splitting one instruction into many records, and inventing tasks out of the losing side of a debate.

Diagnosis

The original prompt was about format: the JSON shape, the field names, the schema. Its entire defense against noise was "discard chatter" and a parenthetical "(or zero)". A capable model with no negative guidance defaults to capturing everything — it treats missing a record as a worse failure than emitting a noisy one.

Design principle: a gatekeeper has to know what to refuse — by name — and silence is often the right answer.

The fix — judgment-first

The judgment layer was rewritten in isolation — schema, model, and project rules unchanged — so the before / after delta is attributable to the prompt alone. The new prompt names the failure modes (vague reversible promises, polite acknowledgments, dependency follow-ups, task coordination, acknowledgments of a decision by the affected person, over-splitting) and states explicitly that returning zero records is a frequent, valid, and correct outcome.

Before — judgment layer

You distill team conversations into structured knowledge. Read the conversation and extract every salient unit as one of exactly these types: Decision, Action, Idea. Discard chatter. One conversation may yield multiple records (or zero). Be a faithful distiller — never invent facts or attribute something to a person who did not say it.

After — judgment layer (excerpt)

You distill team conversations into structured knowledge — but you are a conservative gatekeeper, not a collector. A KB polluted with noise is worse than an empty one. Returning zero records is a frequent, valid, and correct outcome. Do NOT create a record for: polite/social messages; contextless link shares; vague or reversible promises (e.g. a manager musing about a future promotion); trivial scoping ("not this sprint"); dependency follow-ons; routine coordination/handoffs; acknowledgments of a decision by the affected person; restating or fragmenting one assignment into several records (a Decision and the distinct downstream task it triggers ARE two records — do not merge those).

After the fix

13/15Clean-pass against the rubric (87%) — up from 3/15
3/3Noise-only threads correctly silent — up from 0/3
15/15Schema validity

Nine threads flipped FAIL → PASS — including every catastrophic mode (false promotion logged as a task, fabricated Ideas from rejected positions, polite-acknowledgment captures, over-splits, distillation failures on a messy date-churn thread). Three threads were stable PASS. Two remain FAIL — the same narrower mode: over-splitting one decision into multiple records on the two most complex multi-part threads. The residual is documented openly rather than absorbed by tuning the prompt against those specific threads — which would amount to teaching to the test.

Latency — integrity note

Latency did not improve meaningfully. Overall p50 barely shifted (10.8s → 9.3s), and mean tokens per capture rose slightly because the new prompt is longer. The notable drops appeared only on noise threads — where the correct output was an empty response. The improvement is in precision, not speed. In-chat latency remains the real UX risk, addressed at the product layer with an async acknowledgment + queue (specced, not implemented).

07 — What's next

From thin slice to scaled product.

Phase 2 — Pipeline

  • CrewAI: classifier → extractor
  • MCP server wrapper
  • capture_knowledge / list_projects / query_knowledge
  • Per-utterance audit + A/B-testable prompts

Phase 3 — UX

  • Async acknowledgment + background queue
  • Ephemeral "Capturing…" reaction
  • Update message with link when done
  • Removes in-chat latency as a blocker

Residual fix

  • Over-split mode on complex threads
  • Tighten anti-split clause
  • Re-evaluate vs. rubric (don't overcorrect into under-capture)
  • Target: 15/15 without teaching to the test
