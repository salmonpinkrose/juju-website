PRD — In-Flow Knowledge Capture

Product requirements for an AI workflow that turns ephemeral team chat into a typed, queryable knowledge base — the v1 locked spec behind the case study.

01 — Problem & opportunity

Conversation creates knowledge. Scrollback destroys it.

Valuable organizational knowledge — decisions, the reasoning behind them, commitments, sparks of ideas — is created as a byproduct of team conversation (Slack, Zoom Team Chat) and lost to scrollback. Capturing it today requires a context-switch nobody reliably does. The result is fragmented memory, repeated debates, and lost accountability.

The opportunity is to capture that knowledge in the flow of the conversation that already happened, with near-zero friction, as typed retrievable records.

02 — Target user & scope

Narrow persona, broad beneficiary.

Primary persona: a PM or IC working in team chat who wants a thread's decisions, action items, or ideas preserved without leaving the conversation.

Broader beneficiaries: anyone on a project team — IC, design, PM. The persona is kept narrow for focus; the product serves the team.

Privacy reality: some captured content is sensitive (1-1s especially). Notion was chosen because it is collaborative — so shared-vs-private is a real conflict, resolved at the trigger point (see §05).

03 — Goals & non-goals

What v1 commits to — and what it does not.

Goals (v1)Non-goals (v1)
Zero-context-switch capture Automatic / ambient capture
Deterministic typed output Raw transcript archival
Retrievable via filtered views Analytics over the KB
Trustworthy — user controls what is captured and who sees it Multi-workspace; full RBAC modeling

Capture-time visibility (§05) is in-scope and deliberately not a permissions system.

04 — Capture trigger model

Manual, human-in-loop.

v1 capture is invoked explicitly — /capture or a message action on a chosen thread.

Rationale: capture intent is the highest-precision signal available. Manual triggering is lower cost, higher control, and builds trust before any automation. The decision draws on a previously-shipped MVP pattern: ship one controllable slice, earn trust, then expand. Auto-capture is deferred to Future Work (§11).

05 — Visibility model

Hybrid: shared by default, private by explicit flag.

Visibility is decided at capture time, by the same human deciding whether to capture at all.

  • /c/capture → Team KB (shared, default)
  • /c·p/capture private → Private (visible only to the capturer)

This solves the 1-1-vs-team-KB tension without building a permissions system. The human best placed to decide whether to capture is the one best placed to decide who sees it.

v1 implementation (honestly scoped): one Knowledge Capture DB + a Visibility property (Team / Private) + view-level separation (Team views exclude Private). True enforcement (per-user private spaces + Notion ACLs) is production hardening, listed as Future Work. v1 demonstrates the decision point and routing logic, not enforced ACLs — stated plainly.

Requirement — ephemeral confirmation for private captures

A /capture private invocation in a shared channel must reply via Slack's ephemeral message (visible only to the capturer). A public in-thread confirmation of a private note would leak its existence to the channel — defeating the privacy intent.

06 — Extraction taxonomy & contract

Three atomic types. One contract.

Each salient unit of a captured thread is classified into one of three atomic types — Decision, Action, or Idea — and its fields are extracted. One thread can yield multiple records, or zero.

Design principle: faithful distillation, not curated narrative. The capture is an AI distillation of what was actually said. No pre-write edit step (see §08). Capture authenticity outranks user polish.

Per-type body templates (the extraction contract)

TypeType-specific propertiesPage-body template
Decision—Decision · Rationale · Rejected alternative · Implications
ActionOwner · DueContext (why this action)
Idea—Idea · Trigger/context · Potential value · Next step

Shared properties across all types: Name, Type, Date, Participants, Project, Source, Status, Visibility.

Output contract: the LLM returns deterministic JSON — a list of records, each with type, name, shared fields, visibility, body_fields, and source_excerpts. No prose outside JSON.

Requirement — source audit trail (anti-hallucination)

Each record must include source_excerpts — the verbatim message snippet(s) the extraction was derived from. The Notion page appends these in a collapsed audit-toggle at the bottom. This preserves the no-edit / faithful-distillation rule while giving the team an unedited trail to verify against if the AI misattributes or distorts. Trust safeguard, not an edit path.

07 — Notion knowledge model

One database. Many cuts.

A single Notion database — Knowledge Capture — backs all records. Views (Notion UI; the API cannot create them) replace what a folder structure would have done:

  • ADecisions log — Type = Decision, Visibility ≠ Private
  • BOpen actions — Type = Action, Status = Open, Visibility ≠ Private
  • CIdeas — Type = Idea, Visibility ≠ Private
  • DBy project — grouped by Project
  • EMy private — Visibility = Private

Field choices for v1: Project = select (relation later); Status = shared Open / Done / Parked (per-type nuance lives in the body).

Requirement — Project normalization (v1, not deferred)

Before writing, the pipeline fetches the DB's existing Project select options and passes them to the extraction step. The model must snap an extracted project to a semantically-matching existing option; only if genuinely new, create it; if ambiguous, tag Unassigned-Review. Unconstrained auto-create pollutes the DB fast (Project Apollo / apollo-project / Project-Apollo) and breaks the "By project" view. Cheap to add at v1; prevents day-1 rot.

08 — User flow (v1)

Four steps. No edit gate.

  1. Conversation happens in Slack.
  2. User invokes /capture (Team) or /capture private on a thread.
  3. Pipeline: thread text → classify → extract per-type fields → write typed row(s) with Visibility.
  4. Bot replies with link(s) to the created record(s) — ephemeral if private (§05), normal if Team.

No pre-write edit step. Allowing edits reintroduces the manual-summary burden the product exists to remove and invites revisionism — what one wishes the thread had said versus what was actually discussed. Delete is the undo, not edit. Low quality is a model problem to measure and fix (§09), not a UX gate.

09 — Success metrics

Provisional targets, anchored three ways.

Numerical targets are hypotheses to validate, not arbitrary, anchored:

  1. vs. baseline — status quo (manual capture) ≈ 0% effective. The bar is decisively better than the lossy baseline, not perfection.
  2. by cost-of-error, per type — a wrong Idea is cheap (delete); a wrong Decision can mislead the team. Precision is weighted per type by error cost, not a single global number.
  3. provisional → measured — the evaluation is the finding: measured number + diagnosed error pattern + the prompt fix. See the evaluation deep-dive.

Constraint — payload cap (cost + abuse guardrail)

A single /capture must not ingest an unbounded thread (a 400-message thread spikes cost exponentially). v1 truncates to a bounded recent window (message-count or token budget). The constraint is the requirement; the specific limit is a tuned hypothesis.

11 — Roadmap & future work

Built today. Shipping next. Deferred openly.

Phase 2 — Committed

  • Multi-agent classify→extract (CrewAI: classifier agent → extractor agent)
  • MCP server wrapper exposing the capability as MCP tools (capture_knowledge · list_projects · query_knowledge) callable by any MCP client
  • Wrapper, not rewrite — sequenced after the working core
  • Honestly scoped: not built yet at the time of this document

Future Work — Post-v1

  • Enforced private spaces + Notion ACLs
  • Auto-suggest capture (replaces manual trigger)
  • 1:1 container type linking child records
  • Project as relation + Projects DB
  • Analytics over the KB
  • Native Zoom Team Chat action
Why MCP, honestly

The MCP server wrapper mirrors the integration primitive shipped between Zoom and Anthropic in ~April 2026 — meeting decisions becoming actions in external systems. v1 ships direct-API; the Phase 2 wrapper publishes the same capability as the complementary egress direction. The framing is "I implemented the primitive," not "we already use MCP."
