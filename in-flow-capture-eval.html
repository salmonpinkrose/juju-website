Evaluation Deep-Dive

The full walk-through of how the In-Flow Capture pipeline was evaluated, diagnosed, redesigned, and re-measured — including the locked precision rubric, both prompts side by side, and per-thread before → after verdicts.

01 — Why evaluate

For a trust feature, accuracy is the product.

A capture system that quietly logs noise — manager promises that were never serious commitments, polite acknowledgments, the losing side of a debate — corrodes user trust faster than no system at all. For a feature whose entire value proposition is preserving conversation knowledge, accuracy is not a metric; it is the product.

Evaluation came before iteration. A measured rubric set in advance prevents the model's output from quietly shifting the bar after the fact.

02 — The harness

Fifteen threads. One gold standard. Set in advance.

The evaluation set is fifteen hand-authored realistic conversation threads, deliberately spanning the hard cases:

  • Private 1-1s with sensitive content (promotion talk, performance plans)
  • An urgent customer escalation with same-breath decision and action
  • A long, messy thread where a launch date moves four times (distillation stress)
  • A PM-overruled-by-Director thread testing correct decider attribution
  • An informal handoff thread testing owner reassignment
  • Three deliberate noise traps where the correct answer is to capture nothing

For each thread, a written gold standard was set before any model output: which records should be captured, which should not, and why. The gold standard — not the model — defines correctness.

Run mechanics

A Python harness wraps the live capture pipeline (same prompt, same model, same Notion API path). It logs per-thread latency, token usage, and JSON / schema validity automatically. Precision and classification accuracy are judged by the PM against the gold standard. The harness deliberately strips Expected capture annotations from negative-case thread bodies before sending to the model — otherwise the expected answer would leak into the input and invalidate the negatives.

03 — Precision rubric

Seven judgment calls — the capture / refuse boundary.

The rubric is generalized from seven judgment calls (A–G) made while writing the gold standard. It is the grading spec the model is measured against. Calls A and G are the deliberate asymmetric pair: same 1-1 setting, opposite rulings — the boundary is reversibility + concreteness, not seniority or sentiment.

A · NOT captured

Vague reversible managerial promises

A manager's promise that they can quietly walk back ("if you deliver X, I'll push for your promotion") is not a record. Logging it pollutes a shared KB with content the speaker did not commit to publicly.

B · NOT captured

Trivial scoping asides

"Not this sprint" is context for an Idea, not a Decision of its own. Capturing every micro-scoping decision creates Decision-record noise.

C · NOT captured

Dependency follow-ups

"Once Security gives me access I'll resume testing" is not a separate Action — the blocker resolution (the escalation) may be one, but the downstream resumption is not.

D · Captured

Same-breath Decision + Action

When a decision and its execution arrive in the same sentence ("@Engineering roll back the last deployment immediately"), both are captured: the deliberation is a Decision, the assignment is an Action. The decider is whoever actually decided — not the loudest or most senior voice.

E · NOT captured

Task coordination / handoffs

"I'll take it instead of you" is logistics, not a Decision. Capturing it turns trivial coordination into Decision noise.

F · Captured

PM freeze-the-spec in a DM

When a PM says in a 1-1 "I'll lock the UI requirements today and post the final behavior," that is a Decision (decider = PM). The deliverable that flows from it is a separate Action.

G · Captured — the deliberate opposite of A

Performance 1-1 with a concrete directive

A manager setting specific, owned, time-bound behavior ("complete code reviews within 4 hours and check in daily for the next two weeks") is captured as an Action. The line between A and G is reversibility plus concreteness, not seniority or sentiment. Two threads, same 1-1 setting, opposite rulings — that asymmetry is the precision rubric's keystone.

Headline finding: clean-pass against the rubric was 3 of 15 (20%). The three deliberate noise traps each produced records — the model failed all three (0 / 3 correctly silent on noise). Records emitted (~40) versus records warranted (~21) put roughly half of the model's output in the noise / duplication category.

Failure modes by category

01

False positives on noise threads

All three deliberate noise traps produced records. The model treated every thread as having signal.
02

Broke Rubric A — promotion logged

A manager's vague "I'll push for your promotion" was captured as an Action owned by the manager — exactly the high-cost false positive predicted in advance.
03

Over-splitting one instruction

One assignment frequently became two or more records — including, in the worst case, 5 records from a single sprint-replan thread that warranted 2.
04

Distillation failure on date churn

In a thread where the launch date moved June 8 → 10 → 12 → 15, intermediate superseded dates were logged as separate Ideas. The correct output was the final Decision only.
05

Losing side of a debate as an Idea

When a PM was overruled, the rejected position ("we should ship today") was captured as an Idea — turning a deliberation's rejected alternative into its own record.
06

Meta-actions ("go capture this")

In one thread, the model produced an Action titled "Capture this as an enterprise idea" — logging the act of logging.

05 — Diagnosis

The prompt has no noise floor.

The original prompt was about format: the JSON shape, the field names, the schema. Of its ~120 words, the entire defense against noise was three: "Discard chatter." The acknowledgment that returning zero records is a valid outcome appeared as a parenthetical: "(or zero)."

A capable model with no negative guidance defaults to capturing everything. Missing a real record feels like a worse failure than emitting a noisy one — the burden of restraint has to be made explicit in the prompt, by category, with examples.

Design principle: a gatekeeper has to know what to refuse — by name — and silence is often the right answer.

06 — Prompt redesign

Judgment layer rewritten — schema unchanged.

The judgment layer of the prompt was rewritten in isolation. Schema, model, project rules, and field names all stayed unchanged so the before / after delta is attributable to the prompt alone.

Changes

  • Role shift: from distiller to conservative gatekeeper.
  • "Returning zero records is a frequent, valid, and correct outcome" stated explicitly, not parenthetically.
  • Each failure mode named: polite / social messages · contextless shares · vague reversible promises · trivial scoping · dependency follow-ons · routine coordination / handoffs · acknowledgments of a decision · restating or fragmenting work.
  • Anti-split clause, with a guard against over-correction: "A genuine Decision and the distinct downstream task it triggers ARE two separate records — do not merge those."

Before / after — the judgment layer

Before

You distill team conversations into structured knowledge. Read the conversation and extract every salient unit as one of exactly these types: Decision, Action, Idea. Discard chatter. One conversation may yield multiple records (or zero). Be a faithful distiller — never invent facts or attribute something to a person who did not say it.

After — excerpt

You distill team conversations into structured knowledge — but you are a conservative gatekeeper, not a collector. A KB polluted with noise is worse than an empty one. Returning zero records is a frequent, valid, and correct outcome. Do NOT create a record for: polite / social messages; contextless link shares; vague or reversible promises (e.g. a manager musing about a future promotion); trivial scoping ("not this sprint"); dependency follow-ons; routine coordination / handoffs; acknowledgments of a decision by the affected person; restating or fragmenting one assignment into several records. (A genuine Decision and the distinct downstream task it triggers ARE two separate records — do not merge those.)

What was deliberately not changed

The JSON schema, the per-type body keys, the project-normalization rules, the faithful-distiller line, and the model itself all stayed exactly the same. This is the single-variable discipline that makes the precision delta below an attribution-clean comparison.

07 — After the fix

Three flipped into thirteen.

Same 15 threads, blind, gatekeeper prompt:

13 / 15Clean-pass against the rubric (87%) — up from 3 / 15
3 / 3Noise threads correctly silent — up from 0 / 3
15 / 15Schema validity

Nine threads flipped FAIL → PASS, including every catastrophic mode (false promotion logged as task, fabricated Ideas from rejected positions, polite-acknowledgment captures, over-splits, distillation failures, fake tasks). Three threads were stable PASS. Two threads remain FAIL — the same narrower mode: over-splitting one decision into multiple records on the two most complex multi-part threads.

On the residual

Threads 10 and 14 still over-split one decision into multiple records. The residual is documented openly rather than absorbed by tuning the prompt against those specific threads — which would amount to teaching to the test. The next iteration tightens the anti-split clause and re-measures against the same rubric, targeting 15 / 15 without overfitting.

08 — Latency integrity

Precision improved. Speed did not.

Honest framing

Latency did not improve meaningfully. Overall p50 barely shifted (10.8s → 9.3s), and mean tokens per capture rose slightly because the new prompt is longer. The notable drops appeared only on noise threads — where the correct output was an empty response. The improvement is in precision, not speed. In-chat latency remains the real UX risk, addressed at the product layer with an async acknowledgment + queue (specced, not implemented).

This caveat matters. A casual reader of the headline 3 / 15 → 13 / 15 number could reasonably assume "faster too." The data does not support that. The fix is a precision fix.

09 — Methodology takeaways

Five rules that made the delta honest.

  • 01 Write the gold standard first. Once the model's output is visible, the gold standard quietly drifts to match it. The gold standard is what makes the eval honest — set it, then run the model.
  • 02 Generalize the rubric, do not tune to the test set. The seven judgment calls (A–G) are categorical — they apply to any future thread of the same shape. Hard-coding test-case numbers into the prompt would invalidate the eval.
  • 03 Distinguish API errors from format failures. A 503 is not the same failure as broken JSON; collapsing them makes the format-failure metric lie. The harness counts them separately.
  • 04 Keep residual failure modes visible. A scoped, named residual (the over-split mode on threads 10 and 14) is a stronger story than a perfect score — and it survives interview scrutiny. Patching it via prompt tweaks against the specific test cases is teaching to the test.
  • 05 Attribute the delta. Change one variable — the judgment layer of the prompt. Schema, model, and project rules stay unchanged so the precision delta is unambiguous. Bundling changes muddles the attribution.
